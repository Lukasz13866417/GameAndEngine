05 / Demo walkthrough

A mesh file,
all the way to pixels.

Follow the actual colored-cube demo: load a shape, create a renderer, define its shaders and draw a frame. Each step points to the code that does it.

The entry point is examples/file_mesh.cpp. Its FileMeshRenderer owns shader creation and GPU resources. Setup lives in helpers so the example stays readable.

Run itLoadCreateShadeDrawInspect

Before reading the code

Run the example

From the repository root, with a configured build/ directory and OpenGL/GLFW examples enabled:

cmake --build build --target vng_file_mesh_demo -j4
./build/vng_file_mesh_demo

It loads colored_cube.vmesh: a genuinely 3D cube with 24 vertices, 12 triangle faces and different face colors. The camera looks at it from above and to one side. Close the window to exit.

--once deliberately draws one frame and exits. Leave it out if you want to inspect the window. Building/running needs the engine’s Linux/OpenGL setup; reading these pages does not.

1 / File → CPU mesh

Give the fields meanings

The file calls its fields position and color/0. C++ identifies them with semantic types. Position means three floats; Color means four, even when the record stores that color in four normalized bytes.

struct Position : vng::gfx::Semantic<vng::Vec3> {};
struct Color : vng::gfx::Semantic<vng::Vec4> {};
namespace vmesh = vng::content::vmesh;
auto vertex_schema = vmesh::schema<Vertex>();
vertex_schema.map("position", Position{});
vertex_schema.map("color/0", Color{});

vmesh::load(options->mesh_path, vertex_schema) returns the typed CPU mesh or a diagnostic. The schema converts file values to the record’s encoding. No GPU context is needed to parse it.

2 / Explicit lifetime & setup

Let the renderer own its resources

GlfwOpenGLSession::create(...) creates this example’s native window/context and device. Then the application hands its mesh to the concrete renderer:

auto renderer = FileMeshRenderer::create(
    app->device(),
    std::move(*cpu_mesh));

The factory builds shader IR, compiles the normal/diagnostic shader products, uploads the mesh and prepares vertex input. The ready renderer owns that work. Its Renderer<FileMeshDraw> base only identifies the ticket type—it does not hide another renderer or force a fixed technique.

The renderer is created after the session and destroyed before it, keeping the OpenGL context alive while GPU resources are released.

3 / C++ expressions → shader program

Describe the two shader stages

The renderer’s vertex stage projects each position using the supplied camera and passes Color to the fragment stage. The fragment stage receives a symbolic Float brightness argument:

auto fragment = vng::shader::fragment<FragmentIn, FragmentOut>(
    "file_mesh_fragment",
    [](auto& stage, vng::dsl::Float brightness) {
        const auto source = stage.input(Color{});
        const auto color = vng::dsl::vec4(source.xyz() * brightness, source.w());
        stage.observe(SurfaceColor{}, color);
        return stage.output(
            field<vng::shader::Color<0>>(color));
    });

This lambda runs once during construction, recording operations rather than shading a CPU pixel. Linking checks the vertex/fragment contracts. GLSL emission and OpenGL compilation produce the runnable program. Ordinary CPU brightness values are supplied later; changing them does not rebuild the shader.

observe labels a value for optional analysis. It is not another ordinary output attachment in the normal draw.

4 / Ticket → frame

Supply choices for this draw

The application creates std::array draws{FileMeshDraw{}}. A ticket carries instance count, brightness, depth-test/write choices and culling. The camera builds a RenderView for the current image extent; the frame specifies the target size, clear color/depth and output encoding.

if (auto drawn = renderer->render(*frame, *view, draws); !drawn) {
    return example::fail(drawn.error());
}
if (auto ended = frame->end(); !ended) {
    return example::fail(ended.error());
}
if (auto presented = loop.present(); !presented) {
    return example::fail(presented.error());
}

Inside render, the renderer borrows frame commands, sets the ticket’s raster state, calls run(program, brightness), supplies the view, then calls draw(gpu_mesh, instance_count). run selects the program; draw submits geometry. Present happens afterward.

This simple example loops over tickets. A renderer call is not automatically one native draw. The editor’s separate BlueprintMeshRenderer batches compatible tickets into instanced draws.

5 / Inspect the same shader

Ask for rendering evidence

./build/vng_file_mesh_demo --analyze

The demo asks its renderer for a diagnostic sweep before normal drawing, once. It requests the observed surface color along with diagnostic evidence:

auto request = vng::analysis::CaptureRequest::diagnostic()
    .observe(SurfaceColor{});
auto sweep = renderer->diagnose(*frame, *view, draws, request);

Enhanced shader emission uses the same recorded program, with extra identification/observation output. The console report helps connect pixels to geometry and compare raster choices. This example requires one non-instanced ticket for diagnostics; it is not a general full-scene debugger for transparent effects.

Read: analysis_report.hpp, diagnose and validate_diagnostic · Deeper: analysis rendering guide

Small changes to try

These are small C++ edits to make and rebuild; the demo itself is not an editor panel.

  • Change a ticket’s brightness. Only the draw argument changes—not the shader definition.
  • Move the camera. Mesh bytes stay unchanged; the RenderView supplies a new projection.
  • Pass another compatible file: ./build/vng_file_mesh_demo path/to/mesh.vmesh. It needs position/color fields mapped by this schema.
  • Read the direct demo next to see the same boundaries without the concrete renderer wrapper.
