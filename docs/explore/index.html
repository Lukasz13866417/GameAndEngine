About this guide

01 / Start here

A scene, an editor,
and an engine.

Vibe Engine is a C++ engine and an editor being developed together. You describe a scene, the engine draws it, and the editor lets you shape and animate it.

Think of a spaceship: its mesh describes the shape, an instance places a copy in the scene, and a renderer decides how to draw it. The editor changes that same scene data; it is not a separate imitation of the game’s look.

Working with a scene

The editor, at a glance

Viewport & cameras

The viewport is where you see the scene and use manipulation handles, or gizmos. Your private viewing camera is separate from the camera used by the animation.

Blueprints & instances

A blueprint is a reusable definition. Each instance has its own position, rotation, scale and settings. Deleting one ship does not delete its blueprint.

Meshes & regions

Edit a mesh blueprint in its own view. Apply publishes its draft to scene instances; saving alone does not. Regions are per-instance TODO volumes whose boundary points are edited in the scene.

Timeline & keyframes

Keys describe values at timestamps in seconds. Choose how values interpolate. Insert a key to edit a pose between existing keys; the new key starts from the scene you currently see.

Panels & authoring controls

The sidebar has Scene, Keyframe values and Instance properties tabs. Controls edit the selected thing; Undo/Redo treats a gesture as one action. Top bars hold file, view and tool controls.

Preview & Play

A worker process renders the scene while the UI stays separate. Pop-out keeps editing available. Independent Play uses a worker-owned window and can run without debug-image delivery.

Working in C++

The codebase, in broad pieces

Data & files

CPU meshes, vertex records, cameras and file readers describe what exists without a graphics context. Semantic tags such as Position say what a field means, separately from its byte encoding.

Shaders

C++ shader expressions record a typed program once. The engine turns that representation into GLSL, then OpenGL compiles it. Explicit arguments carry changing values for each draw.

Rendering & backends

A renderer accepts small draw tickets, owns its drawing policy and sets state such as depth testing. Neutral contracts describe intent; OpenGL and GLFW supply concrete graphics and window behavior.

Resources & providers

Owners keep buffers, programs and images alive. Providers hold recipes for creating or reloading them. The recipe and the resulting resource are different responsibilities.

Higher-level features

Text, widgets, bloom, rigging, timeline sampling and geometry queries are reusable pieces. They depend on the lower-level contracts they need; there is no single giant engine object.

Applications & tests

examples/ contains demos and the editor. include/vng/ exposes APIs; src/ implements them. Tests cover CPU behavior, GPU rendering and real editor interactions.

A small example: file names become meanings

auto schema = vmesh::schema<Vertex>();
schema.map("position", Position{});
schema.map("color/0", Color{});

The file has named fields; C++ uses semantic tags. The schema connects them. The demo walkthrough follows this exact idea through to a rendered cube.

Three boundaries worth remembering

  1. A blueprint is not an instance. Shared geometry and individual placement are different data.
  2. The document is not the viewport. Looking around should not edit your scene or create undo entries.
  3. A dependency is not an owner. “Needs this to work” is different from “keeps this alive.” The Codebase page shows both explicitly.

A few words you’ll meet

CPU / GPU
The processor running application code / the processor drawing images.
DSL / IR
A small language for describing shaders / the recorded intermediate representation of those calculations.
Backend
The concrete implementation for a graphics or window API, currently OpenGL and GLFW.
Frame
A scoped drawing operation with a target image, image size and drawing context.
